# 设计取舍

这里记录的是「为什么这么做」，尤其是那些看起来可以做但故意没做、或者做起来很钒的地方。
每一条背后都有实测数据。

## 一、为什么是 fork 而不是从零写

需求里明确写了「优先复用或扩展 Chunker」。核实下来的结果是：它确实把最难的几块做好了——
存档格式解析、区块读写、各版本方块映射、数字 ID 转换。这些都是数月量级的工作。

它没做的正好是本工具的核心：

| 缺什么 | 后果 |
|---|---|
| 没有任何报告机制 | 未映射方块**静默变空气**，不报错、不记录 |
| 没有 Y 偏移能力 | 1.18+ 存档（Y=-64 起）转出来是**空地图**，退出码还是 0 |
| 默认保留全部实体 | 输出地图里塞满僵尸、掉落物 |
| 默认搬运容器物品 | 箱子里的东西原样搬过去 |

它的默认哲学是「尽量转过去、转不了就算了」，而本需求是「宁可不转，也要让我知道」。
方向相反，所以报告层不是「加个日志」那么轻，要插进它的静默路径里打点。

## 二、Y 轴平移

### 为什么要平移

1.12.2 的高度范围是 0~255，而 1.18+ 的世界是从 **-64** 开始的。不平移的话，
所有方块都在负座标，被写入器直接丢弃——**输出一张空地图，而且不报错**。

### 为什么对齐 16

区块是按 16 格一个 section 存的。平移量对齐到 16 的倍数后，
平移就等于**只改 section 编号**，方块数据一个字节都不用动。

这不是「省事」，而是**光照正确性的必要条件**：光照数据（BlockLight/SkyLight）挂在 section 上，
会跟着一起搬走。如果不按 16 对齐而逐块搬方块，光照就要单独处理，错位就会导致地图偏暗。

### 为什么只在有负 Y 时才平移

1.13~1.17 的存档方块本来就在 Y≥0，没有平移的必要。
无条件平移会把这些地图白白往下挤，增加被裁的风险。

### 代价（必须知道）

1.18+ 世界高达 384 格（-64~319），平移到 0~383 后，
**超出 256 的那 128 格必然被裁掉**（约 1/3 的高度空间）。
对建在地表的建筑没影响（地表 Y≈63，平移后 127），但建在 Y=200 以上的会被削顶。
所以报告里必须写清楚裁了多少。

## 三、近似替换（275 条规则）

### 为什么不只是「变空气」

用户最初接受静默变空气，但实测发现：用户那张 1.21 的图里有 **20182 个方块**（4.1%）会消失，
其中很多是成片的一一比如整栋楼的楼梯。这不是「损失了几个方块」，是「建筑缺了一块」。

### 替换原则

按优先级：

1. **同形状优先于同颜色**：楼梯→楼梯，墙→墙，活板门→活板门。形状错了看起来是建筑物，
   颜色错了最多是不协调。
2. **同材质族次之**：深板岩矿→主世界同种矿，去皮原木→同木种原木。
3. **颜色只在同形状内匹配**。

举例：`warped_stairs`（下界畸木楼梯）→ 下界砖楼梯，而不是随便一块木头；
`bamboo_trapdoor` → 橡木活板门，而不是消失。

### 用户规则始终优先

界面上写的映射排在内置规则前面，用户指定的方块绝不会被内置规则静默改掉。

### 效果（实测）

| | 之前 | 之后 |
|---|---|---|
| 丢失方块 | 20182 个 | **0 个** |
| 未映射种类 | 225 种 | 2 种 |
| 方块总数 | 971252 | 971252（不变）|

方块总数不变证明是**替换**而非删除。

## 四、增量写入与热更新

这是整个项目最难、也最有价值的一块。

### 真正的病根（和第一直觉相反）

用户的诉求是「改一条映射，右边预览跟着变」。第一直觉是「BlueMap 全量重渲太慢」。

把 BlueMap 的字节码反汇编后才发现真因：它判定「哪些区块需要重渲」靠的是
**每个区块自己的时间戳**（region 头部的一张表，4 字节一个），
拿它跟该图上次渲染的时刻比。

而 **Chunker 从不写这张表**——全仓库搜 `timestamp` 零命中，输出里 16565 个区块的时间戳**全是 0**。

推论：`0*1000 >= 上次渲染时刻` 永远为假 → 一个区块都不重渲。
所以改映射后右侧不是「慢」，是**压根不动**。这个结论和第一直觉完全相反。

### 实测验证

手动给一部分区块写时间戳，再让 BlueMap 重渲：

| 场景 | 耗时 | 重写的 tile |
|---|---|---|
| 首次全量渲染 | 79 秒 | 全部 4265 |
| 输入没改，再渲一次 | 5.3 秒 | **0** |
| 只给 200 个区块打时间戳 | 10.9 秒 | **409**（只渲受影响的）|

证明机制成立。

### 但要先修一个真 bug

实现中发现：**同一张地图、同一套设置，转两次输出字节全部不同**。

一度以为是压缩差异，写脚本解压后逐字段比对才发现：**内容一字不差，差的只是 NBT 字段顺序**。

根因在 `JavaChunkWriter`：两个异步任务（写方块数据、写光照数据）往同一个列表里并发追加，
谁先完成谁先落笔。所以 `Blocks` 和 `SkyLight` 的先后每次都不一样。

> 调试中的两个坑，记在这里避免重踩：
> 1. Python 里 `zlib.decompress(raw[2:])` 是错的——Chunker 写的是**完整 zlib 流**（自带头），
>    跳掉两字节会解压失败。而代码一旦失败回退成「比较压缩字节」，就会得出完全错误的结论。
> 2. 验证脚本漏写 `cli` 子命令时，程序会**启动网页界面干等**，表现为「命令卡住几十分钟」。

改成按字段名排序写入后，同样的输入必得同样的字节。
NBT 规范里 Compound 的字段本就无序，读取方（原版客户端、BlueMap）都不受影响。

### 最终的机制

1. 写入前，先读磁盘上同一区块的字节，**一模一样就跳过**（保留它的原时间戳）
2. 不一样才写，并打上当前时间戳
3. 区块全部写完后，运行一次 `-r` 增量渲染，按时间戳只重渲变更区块；HTTP 查看器保持运行
4. 渲染进程成功退出后才发布预览版本，浏览器完成当前视野的远近层缓存更新后才显示完成

2026-09-14 修正：原先的 `-u` watcher 在区块仍在写入时就可能开始渲染，而且只分配 1 GB 堆。
旧 BlueMap 的线程参数应为 `renderThreadCount`；误用新版的 `render-thread-count` 会回退到大量并发线程。
实际日志出现了渲染线程 `OutOfMemoryError`，但服务进程仍存活，不能用进程存活来代表本轮渲染成功。
现在两版分别使用正确的线程配置，渲染限为 2 个线程、2 GB 堆，并启用 `ExitOnOutOfMemoryError`。
渲染结束标记只在成功后落盘；旧版或未完成的缓存会自动完整修复一次，之后恢复增量。

### 实测结果（1450 个区块的测试图）

| 操作 | 写入区块 | 未变 |
|---|---|---|
| 全新转换 | 1450 | 0 |
| **完全相同再转一次** | **0** | **1450** |
| 加一条 `cobblestone→stone` | **21** | **1429** |

第三条是最关键的：只重写了 **1.4%**，于是渲染从几分钟降到几秒。

### 一个必要的配套改动

重新转换同一张图到同一目录时，**不能把预览进程杀掉重建**，否则就退化成全量重渲。
所以 `LocalApp` 会判断「是不是同一张图→同一个目录」，是的话保留运行中的 HTTP 查看器，
并在本次输出完成后调度增量渲染任务。前端通过 BlueMap 自己的瓦片管理器清理当前视野缓存并重新加载，
同时保留镜头和后续视野使用的缓存版本；不再直接替换场景对象、绕过管理器缓存。

## 五、为什么自己写网页界面，不用上游的 Electron

上游有现成的 React + Electron 界面，但它不适合：

1. **体积**：Electron 壳 + 两个 BlueMap + JRE 会让安装包膨胀到数百 MB
2. **通信方式不同**：它走 stdin/stdout 的 JSON 管道，而本工具需要的是 HTTP（要播 iframe 预览）
3. **改造反而更绕**：需要改它的消息协议去适配新功能

自建一层 HTTP 反而更直接：JDK 自带的 `com.sun.net.httpserver`，**零额外依赖**，
整个工具就是一个 jar。界面是一个单文件 HTML，没有外部资源，也不需要构建步骤。

## 六、两个 BlueMap

没有任何一个版本能同时渲染源地图和 1.12.2：

| 用途 | 版本 | 覆盖范围 |
|---|---|---|
| 左：源地图 | v5.16 | 1.13.2–1.21.11 |
| 右：1.12.2 | v1.5.5 | 1.12.2–1.17 |

v1.5.5 是最后一个支持 1.12.2 的版本；再高就删了（更新说明写着 "Dropped Minecraft 1.12.2 support"）。

**坑**：渲染 1.12.2 时必须显式传 `-v 1.12.2`，否则它会按支持的最新版（1.17）加载贴图，
拿去渲染 1.12.2 的世界——**结果是一张空地图，而且不报错**。这个坑当时表现为「右侧一片黑」，
手测时命令带了 `-v`、写进程序时漏了，典型的「手测通过、自动化没覆盖」。

## 七、jlink 运行时

打包用 jlink 裁出一份自带 Java 运行时（约 63 MB），目标机器不需要装 Java。

模块清单不是拍脑袋来的，是一路报错补出来的：

| 模块 | 不加会怎样 |
|---|---|
| `jdk.crypto.ec` | BlueMap 从 Mojang 下载贴图时 `SSLHandshakeException` |
| `java.sql` | BlueMap 的 Gson 依赖 `java/sql/Time` → `NoClassDefFoundError` |
| `java.desktop` | 选地图文件夹要弹 Swing 选择框 |

少任何一个都会在**运行时**才报错，而且往往是转换到一半。

## 八、已知的未做之事

- 没有在真实的 1.12.2 客户端上做过加载测试（用 BlueMap 渲染作为替代）。
  它能渲染说明格式没错，但**不等于游戏一定能打开**。这是唯一无法自动化的一环。
- 高版本红石行为、命令方块内容不降级。
- 只做 Java 版，Bedrock 方向没做（所以上游的 Bedrock 数据表被排除在仓库外）。
