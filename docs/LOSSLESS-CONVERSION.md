# 无损转换地图：幽灵方块通道

## 当前行为

前端「转换模式」可选择降级转换地图／无损转换地图。两者输出版本均为 Java 1.12.2，复用分析、内容筛选、高度调整、实体处理、增量写盘及 BlueMap 预览。旧客户端未传 mode 时仍按降级转换。

无损模式只加载用户映射，不加载内置近似替换，即使 API 传 approximate=true 也不会开启内置替换。用户显式规则始终优先；没有手动规则、且**原生无法编码**的方块交给下方的幽灵方块通道。1.12.2 可原生表示的普通方块照常编码，不走通道。

默认输出分别为 `<地图名>_1.12.2` 和 `<地图名>_lossless_1.12.2`；用户明确指定输出目录时尊重该路径。

## 幽灵方块通道

### 它解决什么

1.13 以后新增的方块在 1.12.2 里压根不存在，正常降级只能变成空气。实测一张 1.21.11 的建筑图会因此丢掉 **20182 个方块 / 52 种**——不是零星几块，而是楼梯、活板门、栅栏门这类**细节件**，变成空气就是结构上的破洞。

近似替换能填上东西，但填的不是原方块（石英砖变石头）。幽灵通道让这些方块以原样保留。

### 怎么做的

1.12.2 的方块 raw id 空间有 4096 个位置，原版实际只用了 1674 个。那些原版永远不会产生的空位（「幽灵 id」）用来代表高版本方块：

```
转换时：无法原生编码的方块  →  写成一个幽灵 id
服务端：GhostBlocks 插件把幽灵 id 映射回真正的方块
Geyser：转发给基岩客户端，客户端看到的是真实的高版本方块
```

幽灵 id 不占用任何真实方块，所以对原版方块零影响。

### 前提：服务端要装 GhostBlocks 插件

转换出来的存档**必须**由装了 GhostBlocks 插件的 1.12.2 服务端读取。没装的话，幽灵 id 会被服务端解释成 `Block.getById(raw >> 4)` 指向的**另一个真实方块**——不是空气，是错块。

### 状态也会保留

每个幽灵编号对应高版本的**一个具体状态**，不只是方块名。所以楼梯的朝向/上下半/形状、
活板门的开合、栅栏的连接方向、原木的纹理轴向都能原样保留（实测一张 1.21.11 建筑图：
20182 块幽灵方块里，**31 种方块写出了 14215 块多状态数据**）。

这是怎么做到的：幽灵编号从 **32368** 起排（高于所有版本映射空间的上界 32366），
编号在 ViaVersion 的映射表里**原样传递**，直到目标方块「首次出现的那一段」才被换成真实状态。
因为真实数据永远产生不了这些编号，所以不是「尽量少冲突」，而是可证的零冲突。

### 一个已知的取舍：个别状态会回落到最接近的状态

幽灵表里每个方块只枚举了「在版本链里有定义」的状态。极少数状态在目标版本里找不到对应物
（例如 `powder_snow_cauldron` 的 `level=4/6`，或墙的 `south=tall` 这种枚举组合），
这些方块会**回落到同一方块里最接近的那条记录**——按「属性取值相同个数最多」挑，
平局取签名字典序更小的（保证结果可复现）。即「方块对、个别属性不精确」，而不是整块变空气。

实测一张 1.21.11 建筑图，这类回落共 63 块（占幽灵方块的 0.3%），
例如 `east=none,north=none,south=tall,...` 会回落到 `south=low`（只差墙高枚举）。

> **不要用「raw id 最小的那条」当默认态。** 生成器按目标状态 id 升序分配编号，而 bool 属性的
> **下标 0 表示 true**（vanilla 顺序是 `[true, false]`），所以编号最小的那条恰好是
> **所有 bool 都为 true** 的状态——对墙/楼梯/活板门就是 `waterlogged=1`。
> 回落过去会让整片方块变成含水，而它与源状态毫无关系（实测会把 63 块墙变成含水）。

### 幽灵表的来源与同步

表在 `app/chunker/cli/src/main/resources/ghostblocks/channel-patches.txt`，由 GhostBlocks 项目生成，**不要手改**：

```
GhostBlocks/tools/plan-extended.js  →  channel-patches.txt  →  复制到本仓库
```

格式（5 列）：`幽灵rawId|目标方块名|首次出现阶段|目标状态id|状态签名`。
同一个方块会有很多行（楼梯 80 行、栅栏 128 行），靠状态签名区分。

GhostBlocks 升级或重新生成补丁后，重新复制该文件并更新文件头的来源版本号。表加载失败时不会让转换挂掉，而是退回接入前的行为（这些方块重新变成空气，报告里照旧列出）。

## 处理器的接入点

幽灵通道就是内置的一个处理器实现。若以后要接别的处理器（附加实体、资源包等），接法如下。

1. 接口：`app/chunker/cli/src/main/java/com/hivemc/chunker/downgrade/LosslessBlockHandler.java`。
2. 内置实现：`downgrade/GhostBlockHandler.java`；默认注入位置 `ConversionJob.losslessHandler`（不可变字段，初始化时调用 `GhostBlockHandler.createOrEmpty()`）。Web 的预分析和正式转换都创建 `ConversionJob`，两者走同一个默认值。
3. 调度：`LosslessBlocks.needsHandling(...)` 和 `handle(...)`。不要另写扫描器或第二套转换流水线。
4. 真正写入位置：`JavaChunkWriter.writeBlockPalette(...)`，写 Blocks/Add/Data 之前。用户映射不走扩展；接口成功返回后直接写入返回值，不再走原生丢失回退统计。

```java
LosslessBlockHandler handler = block -> {
    // block.identifier() 含完整中间类型和当前状态。
    // block.dimension()/x()/y()/z() 是高度调整后的输出位置。
    // block.nativeValue() 是原生会写成的编码；id 为 0 表示原生表示不了。
    // 处理成功：return Optional.of(new LegacyIdentifier(id, (byte) data));
    // 暂不处理：返回空，交回原生编码，日志与报告仍由本工具负责。
    return Optional.empty();
};

ConversionJob job = new ConversionJob(input, output, output,
        true, true, userMappingsJson, false, true);
job.setLosslessHandler(handler);
job.run();
```

处理器每次任务独立，但同一任务会并发调用，必须线程安全。支持返回 ID 0–4095、Data 0–15，越界会失败。不要逐方块打印或缓存整个世界。

### 判断该不该接管：看 nativeValue，别看名字

`needsHandling` 的准入条件除了「原生无法编码」（`nativeValue.id() == 0`），还包括「在内置近似规则里」。后者会把一些**本来能正确编码**的方块也送进来，此时接管反而是倒退（多一层插件依赖，而且状态会丢）。

内置的幽灵处理器因此用 `block.nativeValue().id() != 0` 直接拒绝。这个判据来自逐块的真实编码结果，比「对照近似规则名单」可靠：实测中，近似规则里确实有 3 个方块同时出现在幽灵表里，其中 2 个（`chiseled_quartz_block`、`prismarine_bricks`）被正确拒绝并继续走原生编码。

### 位序换算（写外部 id 的必看）

返回的 `LegacyIdentifier` **不是** NMS 的 raw id。写盘时 Chunker 把 id 拆成 `Blocks[i] = id & 0xFF`、`Add` 半字节 `= (id >> 8) & 0xFF`；服务端读档时拼回去的是：

```
raw = (Add << 12) | (Blocks << 4) | Data
```

所以要让存档里出现幽灵 raw id `R`，必须返回 `(R >> 4, R & 15)`，直接返回 `(R, 0)` 会得到完全不同的 id。

## 高度调整与出生点

### 为什么需要平移

1.18 以后的世界向下延伸到 Y=-64，而 1.12.2 只能存 0~255。降级时整列上移（命令行 `--shiftToFit`，界面上是「高度调整」），否则越界的 section 会被写盘器**静默丢弃**，得到一个空世界。

### 出生点为什么会被顺手修掉

平移只搬方块、方块实体和实体，`level.dat` 里的出生点是独立字段。现代存档的出生点通常落在负 Y（实测一份 1.21.11 存档是 `Y=-60`），1.12.2 里这个高度根本不存在。服务端读到越界出生点会去找安全点，找不到就拒绝这个世界：

```
[MV] Spawn location from world.dat file was unsafe.
[MV] Original Location: X: 0 Y: -60 Z: 0
[MV] Safe spawn NOT found!!!
```

### 怎么算

survey 阶段本来就要读一遍全图（用来决定往上移多少），顺手把地面高度也量了，没有额外开销：

1. 每个区块按 4 格步长取 16 个采样点，记录该列**最高非空气方块**的 Y。
2. 采样点按 64×64 的格（4 区块）归组，格内累计各高度的出现次数。
3. 全部格合计，**出现次数最多的高度就是这世界的地面高度**。单看一个格会被屋顶带偏（建筑密集处屋顶的列数可能多于地面），全图合计则地面占绝对优势（实测 26%，接近第二名的两倍）。
4. 挑一个「含该高度采样点、且离内容中心最近」的格，用它记住的那一列坐标。
5. 出生点 = 那一列，Y = 地面 + 1（站上去而不是嵌进去），再加上平移量。

### 什么情况下不改

- **已有的出生点仍然可用**（在目标版本合法高度范围内）且**没发生平移**时不动它——那可能是作者特意选的位置。
- 没跑 survey（例如增量预览）时不动。
- 一处地面都没量到（没有主世界内容）时不动。

### 边界

- 只统计主世界：下界的基岩顶棚会把答案带偏。
- 高度会夹到目标版本范围内（1.12.2 为 1..254）。
- **负高度是正常的**：1.18+ 世界里地面在 Y=0 以下很常见，不能当无效值丢掉（踩过这个坑：把负 Y 当作「空列」过滤，结果只剩屋顶，出生点落到 40 格高）。
- 实测同一张图：自动算出 `(-232, 22, 52)`，人工调整的结果是 `(-234, 22, 36)`，高度一致且落点均在实地上。

## 输出与检查

- JSON 报告：`mode` 为 `lossless`；另有 `lossless.pendingBlocks` / `lossless.pending`，列出**进入接口但未被接管**的方块（当前就是原生能编码的那批）。
- `unmapped.blocksLost` 是真正丢失的方块数——**接入幽灵通道后应为 0**。这是判断通道是否生效的主要指标。
- 文本报告开头会写明模式。
- 出生点：`shift` 段会带 `spawnPoint`；落盘后可用 `level.dat` 的 `SpawnX/SpawnY/SpawnZ` 核对。
- 日志：处理器加载成功会打 `[幽灵方块] 已加载 984 个方块；...`。看不到这条就说明表没加载上。

> 报告里的 `unmapped.blocksLostByType` 最长只到 200 条。方块种类多、每种丢得少时，靠它反推「哪些原生无法编码」会漏；要精确判断请用逐块结果。

另有单元测试覆盖普通方块绕过接口、用户映射优先、状态聚合、注入返回编码。所有真实转换测试输出均在独立临时目录，未覆盖用户地图。
