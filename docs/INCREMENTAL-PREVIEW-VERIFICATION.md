# 增量预览完整性修复与验证

## 现场依据

正式结果预览的 `server.log` 出现 `RenderManager-0-17` 抛出 `OutOfMemoryError: Java heap space`。
旧 watcher 只分配 1 GB 堆，而且旧 BlueMap 1.5.5 需要 `renderThreadCount`，此前误写为新版的
`render-thread-count`，因此没有限制住渲染并发。手动渲染使用 2 GB 堆，行为与 watcher 不一致。

另有两处时序/接口问题：转换写完就发布版本，尚未等到 BlueMap 生成全部瓦片；前端把返回 Promise
的 `tileLoader.load(x, z)` 当回调接口使用，并直接替换场景对象，没有更新管理器缓存。

## 当前实现

- 输出完成后运行一次 `-r` 增量任务，保留已有 HTTP 查看器。
- 仅成功退出且出现完整完成标记后发布版本；内存不足立即结束渲染并报告失败。
- 两版各自使用正确的线程参数，渲染限为 2 个线程、2 GB 堆。
- 前端用瓦片管理器自己的卸载和加载流程，等待真实加载队列结束；失败不确认版本。
- 镜头、iframe 和 HTTP 端口保持不变；以后移入视野的瓦片继续使用新缓存版本。
- 旧缓存或中断任务缺少完成标记时，自动完整修复一次；成功后恢复正常增量。
- 结果渲染使用固定路径的稀疏副本，排除历史空区块，保留删除通知和近邻刷新。性能和删除回归见 [结果预览稀疏化](SPARSE-RESULT-PREVIEW.md)。

## 验证

使用隔离目录中的真实 aa 存档，连续执行石英砖→红石块→空气→默认映射。
三轮各重写 217 个区块、保留 150 个不变区块；结果查看器端口一直为 2691、generation 一直为 2。
每轮渲染约 6 秒，浏览器确认的版本依次为 2、3、4，全程没有点击重新渲染或重载 iframe。

对红石映射结果另建完整渲染参考，比较全部 120 个远近层瓦片。
排除随机 UUID 后，网格位置、索引、颜色、UV 等数据没有差异；低精度法线有 147 个值存在
不超过 0.0001 的四位小数舍入差异。材质表 textures.json 的 SHA-256 完全一致。

旧缓存自动修复完成后，再对相同输入执行一次渲染，120 个瓦片文件全部未改写。

Java 全量测试通过；新增 PreviewManager 测试控制渲染完成/失败时刻，验证版本不会提前发布、
原服务不会重启、失败不会变成成功。前端 Node 测试覆盖两层等待、空瓦片、加载失败、重复握手、
队列尚未结束和失败重试，并已接入 CI。未执行 Minecraft 客户端内加载测试。
